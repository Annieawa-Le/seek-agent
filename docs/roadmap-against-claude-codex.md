# SEEK 对标 Claude Code / Codex 演进路线图
> 状态：路线图 v1（pending：等 WebUI 大重构稳定后再启动）
> 定位：SEEK = 为 deepseek 深度优化的 agent 运行时（单模型纵向优化）
> 战略判断：不追"横向兼容"，追"deepseek 生态位第一"——deepseek 便宜、开源权重、国内直连，官方只给 API 不给 agent 运行时，这个生态位是空的
> 差距定性：与 Claude Code / Codex 的差距**不在架构**（循环/工具/MCP/子代理/记忆都已具备），在"打磨厚度"——可靠性闭环、上下文工程、权限模型、并行调度

---

## 一、核心战略

### 三条主线

| 主线 | 对标对象 | 目标 |
|------|---------|------|
| A 日常体验补齐 | Claude Code | 普通用户无人工接管完成"改代码→测试→修复→提交" |
| B 上下文工程重构 | Claude Code auto-compact | deepseek 窗口小、指令跟随弱，上下文工程是**命门** |
| C 并行与规模化 | Codex Cloud | 任务级并行 3-8 个（甜区），不追几十个容器 |

### 三个原则

1. **文件系统是真相，对话是痕迹**：所有压缩方案围绕"信息可拿回"，不是"省 token"。违反此原则的方案（无差别删除）直接否决
2. **单模型调教**：prompt/工具/schema 只对 deepseek 优化，不做模型无关中庸化（那是 Claude Code 的路线，不是我们的）
3. **风险隔离**：新能力进 inner_skills，核心改动走"WebUI 坏→TUI，TUI 坏→人"降级链

## 二、P0 日常体验补齐（对标 Claude Code）

### P0.1 Plan Mode（先方案后执行）
- 现状：无。mode 系统的 manager/worker 是人格切换，不是计划-执行分离
- 做法：`/plan` 指令 → 只读工具集（read/search/kb，无写入/执行）→ 输出方案 → 用户确认 → 进入执行
- 验收：`/plan` 下模型调 write/execute 工具被拒绝；方案确认后才解锁

### P0.2 自动测试闭环
- 现状：测试靠 prompt 引导，无"失败→修复→重跑"循环
- 做法：执行测试命令 → 失败输出回喂模型 → 自动修复 → 重跑，直到绿或放弃（带次数上限）
- 验收：故意引入一个语法错误，agent 能在 3 轮内自愈并报告"测试全绿"

### P0.3 成本/耗时显示
- 现状：无
- 做法：每轮统计 token 消耗（input/output/缓存命中）+ 耗时，WebUI 消息尾部展示
- 验收：一次长对话能看到累计成本，与 API 账单误差 < 5%

### P0.4 交互式权限确认
- 现状：工作区沙箱（workdir.ts）+ listen 审查，无用户确认弹窗
- 做法：危险命令（写系统目录/删除/网络）→ Electron 弹窗 allow/deny/always；记入会话级白名单
- 验收：危险操作触发弹窗，deny 后模型收到明确拒绝信息并改道

## 三、P1 上下文工程重构（deepseek 命门）

> 历史教训（已弃用的三个方案及其死因，重构时不要再踩）：
> - memory_focus：**不可逆丢失**（splice 删原文，梗概漏=永久丢）；**按轮次触发**（一轮 2~50 条消息，预算失控）
> - memory_shorten：**无差别缩短**（非幂等工具输出丢失，后续无法引用）
> - desk：**常驻成本 vs 收益不匹配**（全文注入占 token，且工作区变化后内容易过期）

### P1.1 预算触发自动压缩
- 做法：工具循环后读 usage，超预算自动压缩（**系统级触发**，不靠模型自觉调 memory_focus——长任务里模型不会记得主动清理，这是旧方案效果差的一半原因）
- 验收：长对话中模型无需干预，上下文自动维持在预算内

### P1.2 压缩产物固定 schema
- 做法：每条记录 = 用户原意（截断）/ 关键决策 / 文件改动 / 待办 / **取回指引**（重读哪个文件、重跑哪个命令）。不产出散文梗概，产出结构化导航
- 验收：压缩后模型能凭梗概定位"该去哪拿细节"，不依赖散文回忆

### P1.3 按幂等性分级缩短
- 做法：read/search/kb 幂等 → 输出可压成 success（需要时重调，成本低）；execute_command/写操作不幂等 → 输出保留或落盘到文件
- 验收：压缩后模型能回答"你刚才跑的命令输出是什么"（从落盘文件读回）

### P1.4 desk 两级化
- 做法：常驻只放每文件 3 行摘要（<50 token/条）；全文一律 read_file 按需。常驻注入只配给"稳定的约定"（类 CLAUDE.md），代码内容永远不配常驻
- 验收：desk 单轮注入总成本 < 1k token，且模型遇到"需要细节"时主动 read_file

### P1.5 压缩可逆（Claude Code 核心技巧）
- 做法：压缩时保留原始消息的引用（raw 副本），二次压缩可重新提炼——信息可逆，压缩就不怕漏
- 验收：连续压缩三轮后，模型仍能恢复第一轮的关键细节（从 raw 重提炼）

## 四、P2 可靠性与恢复

### P2.1 Checkpoint / Resume
- 做法：工具调用序列落盘（工具名+参数+结果摘要），进程崩溃后可从最近 checkpoint 续跑
- 验收：模拟进程被杀，重启后 agent 能说明"我做到哪了"并继续

### P2.2 工具失败重试与自愈
- 做法：可重试错误（网络/超时/限流）自动退避重试；不可重试错误回喂模型调整策略
- 验收：断网 5 秒场景 agent 自动重试成功；永久失败场景 agent 改道，不重复撞墙

## 五、P3 并行与规模化（对标 Codex）

> 定位：进程内子代理（现）→ 任务级并行（目标）。**不追 Codex 的容器级几十并发**——本地运行时无云端算力，且共享文件系统撑不住几十个同时写。3-8 个任务级并行 + 独立工作目录是甜区

### P3.1 任务调度器
- 做法：任务队列 + 并发上限（默认 3-5）+ 失败重试退避 + 优先级
- 验收：喂 10 个独立任务，按并发上限分批跑完，无文件冲突

### P3.2 工作目录隔离
- 做法：每任务独立临时目录或 git 分支；同文件多任务写 → 冲突检测（报错/排队），不静默覆盖
- 验收：两个任务同时改同一文件，第二个被拒绝或排队

### P3.3 每 agent 配额管理
- 现状：子 agent 共享同一 provider（为命中 prompt 缓存），并发会互相踩限流
- 做法：每 agent token/请求配额 + 共享限流池
- 验收：6 并发下无 429 风暴，总吞吐不降反升

### P3.4 结果聚合与失败隔离
- 做法：子任务完成 → 结构化结果 → 主 agent 汇总；单任务崩不影响队列其他
- 验收：10 个任务中 2 个失败，其余 8 个照常完成，失败 2 个有明确报告

## 六、P4 生态与可信

### P4.1 MCP 深化
- 现状：客户端已实现（src/mcp/，兼容 Claude Desktop 配置格式），无配置 UI
- 做法：mcp.json 可视化配置 + MCP 状态面板（连接/错误/工具列表）
- 验收：用户在 WebUI 加一个 MCP server，不碰命令行，工具立即可用

### P4.2 SEEK.md 约定文件（CLAUDE.md 等价物）
- 做法：工作区根目录 SEEK.md 由用户书写项目约定（架构/规范/禁忌），自动注入 prompt
- 验收：用户写"测试用 Vitest"，后续所有任务 agent 自动遵守，无需每次叮嘱

### P4.3 Hooks 系统
- 做法：pre/post 工具钩子（用户可写脚本：工具调用前拦截/调用后检查/失败告警）
- 验收：用户写一个"任何 delete 前打印警告"的 hook，实际生效

### P4.4 权限模型落地（P0.4 完整版）
- 做法：allow/deny/ask 三级 + 危险命令分类表 + YOLO 模式开关
- 验收：与 P0.4 合并验收

## 七、P5 打磨（不着急）

| 项 | 决策点 |
|----|--------|
| TUI 输入框 | **冻结**（应急通道稳定优先）或换库重写（Ink/blessed）。手写渲染层 5w+ 字符天花板已到，不建议继续修 |
| diff 审查视图 | WebUI 展示文件改动 diff，用户可逐块接受/拒绝（对标 Claude Code edit 模式） |
| 消息折叠 | 长工具输出默认折叠，点击展开 |

## 八、不做清单（避免过度工程）

- 不追 Codex 的容器级几十并发（本地运行时无云端算力，3-8 任务级并行是甜区）
- 不做模型捆绑（BYOM 是定位不是缺陷；deepseek 生态位是护城河）
- 不推平自举系统的"地质层"（工具间隐式依赖是踩坑踩出来的知识，重构时当约束不当垃圾）
- 不做模型无关中庸化（那是横向兼容路线的妥协，我们走纵向优化）

## 九、风险与原则

- 自举系统隐式依赖：patch 系统历史包袱、inner_skills 的 ESM 模块缓存怪癖——改动前先看 `history_patch`
- 每次核心改动重启验证，走降级链：WebUI 坏了 TUI 上，TUI 坏了人上
- 测试与历史兜底：`scripts/test-*.ts` 回归 + `.seek-agent/history/` 跨会话撤销
- 上下文工程一切方案围绕"信息可拿回"；违反此原则（无差别删除/不可逆压缩）直接否决

## 十、总验收：日常体验清单

一个普通用户在 WebUI 完成以下流程，全程无需人工接管：

1. 描述一个任务（改 3 个文件 + 加测试）
2. agent 产出方案 → 用户确认（Plan Mode）
3. agent 改代码 → 自动跑测试 → 失败 → 自愈 → 全绿
4. 用户能看到改了哪些文件、花了多少钱、耗时多久
5. 中途进程崩溃 → 重启后 agent 从 checkpoint 续跑
6. 期间任何危险操作都有弹窗确认

这 6 条全过 = 对标成功。当前状态：全不满足。
